# Практика: FR и NFR для **своего** проекта

**Курс:** Архитектура ПО / Software Architecture  
**Формат:** индивидуальная / парная раздатка Markdown (дома или 2×80 мин)  
**Лекции:** `04-functional-requirements.tex`, `05-non-functional-requirements.tex`  
**Связанная практика (общие примеры):** [`04-fr-nfr-practice.md`](04-fr-nfr-practice.md)  
**Задача:** применить FR (*functional requirements*) и NFR (*non-functional requirements*) к **вашему** курсовому / командному проекту — не к учебному кейсу из лекции.

---

## Цели

1. Кратко описать проект (паспорт).
2. Сформулировать **8–12 FR** (shall и/или user story); для **≥4** — критерии приёмки (*acceptance criteria*).
3. Сформулировать **6–8 NFR** как измеримые сценарии качества (стимул → ответ → мера).
4. Отбраковать 3 «не-требования» (решения, UI-шелуха, размытость).
5. Свести FR и NFR своего проекта в одну таблицу-контраст.
6. Зафиксировать один **компромисс** (*trade-off*) между двумя NFR.
7. (По желанию) пройти peer review по чек-листу.

## 3. Нефункциональные требования (6–8 NFR)

Сделайте NFR **сценариями**, не лозунгами. Шаблон одной строки:

> **Когда** \<стимул\> **при** \<условиях\> **система** \<ответ\> **мера:** \<число или однозначный исход\>.

Покройте разные атрибуты качества (*quality attributes*), например: performance, reliability, availability, security, usability, maintainability, scalability, compliance — берите то, что реально важно *вашему* проекту.

## 4. Отбраковка: что *не* является требованием

Выпишите **три** формулировки, которые вы (или заказчик) могли бы сказать про проект — но это **не** требования. Для каждой: тип и почему отвергли.

Типы: **D** = решение / дизайн / стек (*design decision*); **UI** = диктат интерфейса без поведения; **V** = размытость (*vague*).

| # | Формулировка | Тип (D / UI / V) | Почему это не FR и не NFR | Как переписать, если нужно |
|---|--------------|------------------|---------------------------|----------------------------|
| 1 | | | | |
| 2 | | | | |
| 3 | | | | |

Примеры направлений (не копируйте слепо): «возьмём Firebase», «кнопка зелёная», «система должна быть современной».

## 7. Что сдать (deliverable)

Один файл на человека или команду (Markdown / Google Doc / PDF — как скажет преподаватель), имя вроде:

`FR-NFR-<фамилия-или-команда>-<название-проекта>.md`

**Обязательный состав (по порядку разделов 1–6):**

1. Паспорт проекта  
2. Таблица 8–12 FR  
3. Acceptance для ≥4 FR  
4. Таблица 6–8 NFR-сценариев (+ non-goals)  
5. Три отбраковки  
6. Таблица FR vs NFR + короткий абзац про архитектуру  
7. Trade-off с компромиссом  

Объём ориентир: 3–6 страниц A4, без воды и без копипаста лекций.

---

## Советы 

- Сначала функции, потом качества: NFR без FR часто превращаются в фантазии.
- Если не можете придумать меру — требование ещё сырое.
- Учебный срок ≠ SLA банка: честные non-goals повышают оценку ясности.
- Этот документ потом можно приложить к мини-проекту архитектуры (недели 14–16).
