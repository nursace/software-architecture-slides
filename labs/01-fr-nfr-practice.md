**Ключевые слова:** FR (*functional requirements*), NFR (*non-functional requirements*), acceptance criteria, quality scenario, trade-off

---

## Цели

1. Отсортировать утверждения на **FR / NFR / решение / мусор**.
2. Переписать ≥4 плохих требования в проверяемые FR или NFR.
3. Для 2 FR написать **критерии приёмки** (*acceptance criteria*).
4. Для 2 NFR написать **сценарий** (стимул → ответ → мера).
5. Явно указать одну пару **конфликтующих** NFR и компромисс.

## Разминка — сортировка (10 мин)

Пометьте каждое: **F** (FR), **N** (NFR), **D** (design/решение), **X** (размытый мусор).

1. Покупатель добавляет товар в корзину.  
2. p95 открытия карточки товара < 300 мс при 500 RPS.  
3. Использовать Kafka и Kubernetes.  
4. Система должна быть современной и удобной.  
5. Преподаватель выставляет оценку 0–100 за сдачу.  
6. 99,9% аптайма API оплаты за календарный месяц.  
7. Кнопка «Оплатить» синяя и справа внизу.  
8. При обрыве сети черновик домашки сохраняется локально и синхронизируется позже.  
9. Пароли хранить в salted hash; админские действия — только с MFA.  
10. Микросервисы обязательны.

**Ключ (обсудить):** 1 F; 2 N; 3 D; 4 X; 5 F; 6 N; 7 X/UI (не FR); 8 F (поведение деградации) + можно добавить N рядом; 9 N (security); 10 D.

## Активность A — Переписать FR (≈20 мин)

Выберите **один** домен на команду: банк / e-commerce / чат / кампусный портал / IoT.

### Шаг 1. Возьмите сырые формулировки

Перепишите каждую в **атомарный FR** (+ 2 acceptance criteria для двух лучших):

| # | Плохо | Ваш FR | Acceptance (кратко) |
|---|-------|--------|---------------------|
| 1 | Система поддерживает платежи | | |
| 2 | Удобная сдача файлов | | |
| 3 | Чаты в реальном времени | | |
| 4 | Управлять пользователями | | |
| 5 | (своя плохая фраза) | | |

**Подсказки**

- Избегайте: support / manage / handle / «как у Amazon».
- Не диктуйте стек и цвет кнопок.
- Shall *или* user story — но результат должен быть наблюдаемым.

### Шаг 2. Мини-пример «до/после» (эталон)

- Плохо: «Система поддерживает уведомления.»  
- Лучше (FR): «При статусе заказа `ready` система отправляет push владельцу заказа с номером и временем.»  
- Acceptance: нет push → заказ всё равно `ready` в БД; повтор статуса не шлёт 10 писем подряд (дедуп 5 мин).

### Банк плохих NFR → перепишите

1. «API должен быть быстрым.»  
2. «Данные должны быть в безопасности.»

## Советы преподавателю

- Споры «это FR или NFR?» решайте тестом: *поведение vs мера качества*. Серые зоны (offline-режим) допустимы, если оба аспекта записаны явно.
- Если команда пишет стек в FR — верните вопрос: «Какое *поведение* пользователя от этого меняется?»
- Свяжите с неделей 2 (атрибуты качества) и неделей 3 (модули страдают от размытых FR).
